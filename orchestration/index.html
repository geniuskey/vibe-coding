  • 😊 1주차 — "네, 요구사항 다 파악했습니다"순항
  • 🗂 4주차 — 메모·회의록·시안이 머릿속에 가득과적
  • 🌀 7주차 — 폐기한 v1 시안과 최신 v3가 뒤섞이기 시작혼선
  • 🫠 9주차 — "그런데 원래 목표가 뭐였죠?"표류
에이전트 하나에 긴 작업을 맡겨도 똑같은 일이 벌어집니다.
작업 기억(컨텍스트 창)이 차면 흐려집니다 — 원리는 context 세미나에서. 오늘은 "그래서 어떻게 나누나".

한 명의 한계

방향키로 한 줄씩. 유능한 신입 비유: 능력이 아니라 작업 기억의 문제입니다. 9주차 신입은 게을러진 게 아니라 폐기안과 최신안이 뒤섞였을 뿐입니다. 에이전트도 같습니다. 해법은 사람 조직이 이미 찾았습니다 — 나누고(분업), 요약해 맡기고(위임), 결론만 받는다(보고). 이게 다음 장입니다.

CH 2 · 서브에이전트의 원리

서브에이전트는 세 박자로 일합니다 — 위임 → 격리 → 보고

🤖부모 에이전트 긴 대화 · 전체 계획 보유
📨 임무 요약 ↓ ↑ 결론만 📋
🔍자식 A 시행착오는 여기서
🧪자식 B 시행착오는 여기서
  • ① 📨 부모는 임무를 요약해 위임합니다 — 대화 전체가 아니라 지시서 한 장
  • ② 🧼 자식은 깨끗한 자기 컨텍스트에서 일합니다 — 부모의 긴 히스토리를 모른 채
  • ③ 📋 돌아오는 건 요약뿐 — 자식이 읽은 1만 줄은 부모에게 넘어오지 않습니다

부모의 상자는 계획과 결론만으로 가볍게 유지됩니다 — 회사의 분업·위임·보고와 같은 구조입니다.

오늘의 뼈대. 방향키로 세 박자를 하나씩: 위임(요약된 지시서) → 격리(자식만의 새 작업 기억) → 보고(요약만 돌아오고 자식의 상자는 버려짐). 팀장이 실무자의 시행착오 기록을 다 읽지 않는 것과 같습니다. 자식은 부모의 대화를 모른다는 점이 직관과 다른 부분 — 그래서 다음 장의 "지시서"가 중요합니다.

자식이 읽은 1만 줄은 자식의 상자에서 끝납니다

자식: 1만 줄 읽음 다 쓰고 버려짐 ♻️
→요약 30줄 +2K
부모 에이전트

자식이 읽은 1만 줄은 자식과 함께 사라지고, 부모에게는 결론 30줄만 남습니다.

🧮 함수 분리와 같은 원리

지역 변수 = 자식의 탐색·시행착오   반환값 = 요약 보고   호출자 = 부모

이것을 컨텍스트 격리라고 부릅니다 — 서브에이전트를 쓰는 가장 큰 이유.

격리의 경제학: 대량 읽기·시행착오라는 지저분한 토큰 소비를 자식 상자에 가두고, 부모는 정제된 결론만 받는다. 함수 비유(지역 변수/반환값/호출자)는 context 세미나에서 이어받은 것 — 청중에게 연결고리를 명시적으로 짚어준다.

CH 3 · 오케스트레이션 패턴

팀을 짜는 방법은 패턴 4가지면 충분합니다

① 🎭 역할 분담

탐색 → 계획 → 구현 → 리뷰. 단계마다 다른 에이전트, 각자 깨끗한 눈.

읽을 건 많고 단계가 뚜렷할 때

② 🍴 병렬 fan-out

독립 작업 여러 개를 동시에. 기다리는 시간이 줄어듭니다.

보고서 10개 요약 · 후보 3개 비교 조사

③ 🏭 파이프라인

항목별로 단계를 흘려보내기 — 앞 단계 전체를 기다리지 않고.

문서 50건 추출 → 번역 → 검수

④ ⚖️ 심판 패널

같은 문제를 N번 독립 시도 → 채점·종합. 서로 반박도 시킵니다.

설계안·문안처럼 정답이 여럿일 때

네 이름과 한 줄 정의를 먼저. 역할 분담 = 단계별 전문가, fan-out = 같은 일을 여러 명이 나눠 동시에, 파이프라인 = 생산 라인, 심판 패널 = 경쟁시키고 채점. 뒤의 상세는 잊어도 이 네 이름과 마지막 한 장 정리만 가져가면 됩니다. (파이프라인·심판 패널 상세는 전체 보기에서)

① 역할 분담 — 단계마다 새 눈을 씁니다

🔍탐색 코드베이스를 뒤져 보고서만 잡동사니는 여기 두고 감
→
📐계획 보고서만 보고 설계 새 상자
→
🛠구현 계획서대로, 잡음 없이 새 상자
→
🧐리뷰 남의 눈으로 코드만 새 상자

탐색이 읽은 파일 수십 개는 탐색 상자에 두고 갑니다 — 계획은 정리된 보고서만 보고 세웁니다.

리뷰어는 구현자의 사정을 모릅니다. 내가 만든 것은 내 눈에 늘 옳아 보이니까요 — 사람도, 에이전트도.

역할 분담(탐색 → 계획 → 구현 → 리뷰)의 포인트는 "각자 새 눈". 탐색의 잡동사니 위에서 계획을 세우지 않고, 구현자의 자기 합리화가 리뷰에 스며들지 않습니다. 검증 세미나의 "다른 눈 리뷰"가 바로 이 패턴입니다. 단계 사이 인수인계는 보고서 파일로 — 다음다음 장.

조건: 서로 독립 같은 파일 금지

예: 보고서 10개 요약 · 후보 3개 비교 조사 · 파일별 변환. 걸리는 시간은 줄지만 드는 토큰은 줄지 않습니다.

방향키로 아래 그림을 띄웁니다. fan-out의 이득은 기다리는 시간 — 총 작업량(토큰)은 오히려 늘 수 있습니다. 조건: 조각이 서로 독립일 것 — 서로의 결과를 기다리지 않고, 같은 파일을 고치지 않고. 조사 작업의 fan-out은 Anthropic 멀티에이전트 리서치 시스템이 대표 사례입니다.

문서 A가 검수받는 동안 문서 C는 추출 중 — 단계별로 다 모일 때까지 기다리지 않으면 라인이 쉬지 않습니다.

const files = await agent('점검할 파일 목록')
const found = await pipeline(files.list, f =>
  agent(`${f} 단위 오류 점검`))      // 🍴 fan-out
const ok = await parallel(found.map(x => () =>
  agent(`반박해 봐: ${x}`)))           // ⚖️ 심판

🧠 계획이 상자 밖으로

중간 결과는 스크립트 안에 — 메인 대화엔 최종 보고만 돌아옵니다.

🔁 다시 돌릴 수 있다

잘 된 실행은 /workflows에서 s로 저장 → 다음부턴 /내-이름 한 줄. 중간에 멈춰도 끝난 에이전트는 다시 안 돕니다.

💸 비용은 ×N

에이전트 25개·150만 토큰을 넘으면 경고가 뜹니다. 폴더 하나로 먼저 시험해 보고 넓히세요.

Dynamic workflow: Claude가 작업에 맞는 JavaScript 스크립트를 써서 백그라운드에서 실행한다. agent()는 자식 하나, pipeline()은 목록 항목마다 하나씩, parallel()은 동시에 여럿 — CH3의 fan-out·파이프라인·심판 패널이 그대로 함수 이름이 된 것. 시작: 프롬프트에 "workflow로"라고 직접 요청하거나 ultracode 키워드. 내장 예시로 /deep-research(여러 출처를 교차 검증하는 조사)가 있어 데모하기 좋다. 서브에이전트와의 차이: 서브에이전트는 Claude가 턴마다 판단하고 결과가 메인 컨텍스트로 들어온다. Workflow는 스크립트가 루프·분기·중간 결과를 쥐고, 메인 대화엔 최종 답만 온다. 그래서 수백 파일 마이그레이션·전수 점검에 맞다. 비용 경고: 에이전트 25개 또는 예상 토큰 150만을 넘으면 Large workflow 경고. Pro 요금제는 /config에서 켜야 하고 기본 규모 가이드는 medium(10개 미만, Pro 요금제는 small·5개 미만). 작은 조각으로 먼저 돌려 비용을 가늠하는 습관. 판단 기준은 여기서도 같습니다 — 작고 순차적인 일에 Workflow를 쓰면 비용만 늡니다.

🏭 파이프라인항목이 많고 단계가 고정"문서마다 추출 → 번역 → 검수 순서로, 끝난 것부터 다음 단계로 넘겨줘."
⚖️ 심판 패널정답이 여럿, 품질이 승부"서로 다른 접근으로 3번 따로 시도한 뒤, 비교·채점해서 가장 나은 안을 제안해줘."
