🤖 "요청하신 기능 구현을 완료했습니다.
   모든 케이스에서 정상 동작하며,
   기존 코드와도 완벽히 호환됩니다."
✓ 컴파일 ✓ 실행 ✓ 자신감

이 자신감, 어디까지 믿으시겠습니까?

컨텍스트·지식 세미나에 이은 심화 트랙 세 번째: AI가 만든 결과물을 어떻게 믿을 것인가. 오늘의 부제는 "돌아간다 ≠ 맞는다" — 코드가 실행된다는 것과 올바르다는 것 사이의 간극을 메우는 도구들을 다룬다.
CH 1 · 신뢰 격차

무섭게 틀리지 않고, 그럴듯하게 틀립니다 — 방향키로 진행하세요 ▸

def is_expired(token):
    """토큰 만료 여부를 반환"""
    now = datetime.now()
    return now > token.expires_at

# 리뷰어: "깔끔하네요 👍" · 내 PC에서 테스트 통과
✓ 컴파일 통과 ✓ 실행 성공 ✓ 테스트 통과 (내 PC)
🔍 서버는 UTC, now()는 로컬 — 한국에서만 9시간짜리 버그

완전히 틀린 코드는 금방 걸립니다. 무서운 건 90% 맞는 코드 — 컴파일러도, 실행도 잡아주지 않습니다.

AI 코드의 진짜 문제는 '틀림'이 아니라 '그럴듯하게 틀림'입니다.
훅: 멀쩡해 보이는 4줄짜리 함수. 컴파일되고, 돌아가고, 같은 시간대인 내 PC에서는 테스트도 통과한다. 그러나 서버는 UTC — 배포하면 9시간 어긋난다. 이런 "90% 맞는 코드"가 AI 코드의 전형적 실패 모드다. 완전히 틀린 코드는 금방 걸리지만 그럴듯하게 틀린 코드는 검증 체계 없이는 못 잡는다는 것이 오늘의 출발점.
CH 1 · 신뢰 격차

미묘하게 틀리는 단골 패턴 도감

📏 경계값> vs >= — 재고 0개, 마지막 날, 최대치에서만 하루씩 어긋납니다
⚖️ 단위·스케일ms와 s, %와 비율(10 vs 0.1), nm와 µm — 숫자는 나오는데 자릿수가 다릅니다
🕐 시간대UTC vs KST, 서머타임 — 내 PC에서는 절대 재현되지 않는 버그
🤫 조용한 실패except: pass, 빈 리스트 반환 — 에러가 안 나서 더 무섭습니다
👻 환각 API그럴듯한 이름의 존재하지 않는 함수·옵션 — 설명은 아주 자신 있게 붙습니다
공통점: 한 번 돌려보는 것만으로는 안 잡힌다 — 경계를 찌르는 검증이 필요합니다.
AI가 미묘하게 틀리는 5가지 단골 패턴: 경계값, 단위·스케일, 시간대, 조용한 실패, 환각 API. 반도체 데이터 다루는 분들에게는 단위·스케일(nm/µm, %와 비율)이 특히 아픈 패턴. 다섯 패턴의 공통점은 "행복한 입력 한 번 돌려보기"로는 절대 안 잡힌다는 것 — 뒤에서 경계값 테스트로 회수한다.

✈️ 자동화 편향

자동조종·내비게이션 시절부터 검증된 인간의 버그 — 기계가 말하면 덜 의심합니다.

🗣 유창함의 함정

매끄러운 설명 = 맞다는 착각. 말투는 품질 신호가 아닙니다. 폰트가 예쁜 보고서가 왠지 믿음직해 보이는 것과 같습니다.

🪞 이중 잣대

동료 코드는 꼬치꼬치 의심하면서, AI 코드는 LGTM 👍 — 내가 안 짰는데 내 코드가 됩니다.

📉 METR 2025 실험: 숙련 개발자들이 AI 도구를 쓰며 실제로는 19% 느려졌지만, 스스로는 "20% 빨라졌다"고 답했습니다 — 체감은 측정이 아닙니다.
자동화 편향(automation bias)은 AI 이전부터 항공·의료에서 연구된 현상 — 사람은 자동 시스템의 출력을 과신하고 교차 확인을 생략한다. LLM은 유창함 때문에 이 편향을 더 세게 자극한다. METR의 2025 RCT는 숙련 오픈소스 개발자 기준이라 일반화에는 주의가 필요하지만, "체감 속도와 실제 속도가 정반대일 수 있다"는 메시지로는 충분하다.

최악의 발견 지점

버그가 코드 리뷰가 아니라 보고서에서 발견됐습니다 — 검증은 미룰수록 비싸집니다.

이해 없는 커밋 = 남의 코드

디버깅의 절반은 "이 코드가 뭘 하는지" 알아내는 시간이었습니다.

바이브 코딩의 속도는 검증이 병목이 되는 순간 무너집니다.
전형적 시나리오: 생성은 10분, 그러나 검증을 설계하지 않아 디버깅에 3일. 합계로 보면 손으로 짜는 것보다 느리다. 포인트 두 가지 — 버그가 가장 비싼 지점(보고서·프로덕션)에서 발견됐다는 것, 그리고 이해 없이 커밋한 코드는 디버깅 시점에 남의 코드가 된다는 것.

사다리 꼭대기 — 사람 없이 도는 검증

🪝 커밋 훅

커밋하는 순간 lint·타입 체크·빠른 테스트 자동 실행 — 이상하면 커밋 자체를 거절합니다.

♻️ CI 파이프라인

푸시할 때마다 깨끗한 환경에서 전체 테스트 — "내 PC에서는 되는데요"를 차단합니다.

🤖 AI 리뷰 봇

PR마다 1차 리뷰를 자동으로 — 사람 리뷰어가 보기 전에 뻔한 문제를 걸러줍니다.

AI가 만든 코드도 같은 관문을 통과해야 합니다 — 사람 봐주기 없기.

한 번 세팅해두면 이후의 모든 커밋이 공짜로 검증됩니다 — 세팅 자체도 에이전트에게 시키면 됩니다.

사다리 5단: 커밋 훅(로컬 즉시), CI(푸시마다 깨끗한 환경), AI 리뷰 봇(PR마다 1차 스크리닝). 핵심 메시지는 두 가지 — AI가 만든 코드도 예외 없이 같은 관문을 통과시킬 것, 그리고 이 세팅 작업 자체가 에이전트에게 시키기 좋은 작업이라는 것.

CH 3 · 테스트가 지렛대

테스트 = 실행 가능한 스펙

📜 스펙이자 문서

"이 입력엔 이 출력"— '맞음'의 정의를 산문이 아니라 코드로 적어둔 것.

🤖 기계가 판정

사람이 코드를 안 읽어도 초록/빨강으로 판정 — AI에게 넘겨줄 수 있는 완료 기준이 됩니다.

♻️ 한 번 쓰면 평생 일함

다음 수정·다음 세션·다음 사람까지 지켜주는 회귀 방지선.

코드 생산이 싸질수록 검증의 가치는 올라갑니다 —
테스트는 AI 시대에 값이 오른 몇 안 되는 자산입니다.
왜 테스트가 지렛대인가: 사람이 diff를 안 읽어도 기계가 "맞음"을 판정해주기 때문에, 검증의 사다리에서 사람 노력을 크게 떨어뜨리는 첫 단계다. AI 시대에 코드 생산 비용은 급락했지만 "이 코드가 맞는가"의 비용은 그대로 — 그래서 테스트의 상대 가치는 오히려 올랐다. 에이전트에게 일을 시킬 때도 "테스트 통과"는 가장 명확한 완료 기준이 된다.
CH 3 · 테스트가 지렛대

테스트 먼저 시키기 — 에이전트와 TDD

STEP 1🔴 실패하는 테스트 작성구현 금지 — 기대 동작만 코드로. 사람이 이 테스트를 확인
STEP 2🟢 통과할 때까지 구현에이전트가 실행→실패→수정을 스스로 반복
STEP 3✨ 리팩터링 & 재확인테스트가 초록인 상태를 유지하며 정리
"먼저 이 기능의 실패하는 테스트부터 작성해줘. 구현은 아직 하지 마.
 내가 테스트를 확인하면, 그때 통과할 때까지 구현해줘.
 테스트 코드는 수정하지 말고."

에이전트 루프(실행→관찰→수정)에 명확한 목표 함수가 생깁니다 — 끝났는지를 사람이 아니라 기계가 판정.

TDD가 에이전트와 찰떡인 이유: 에이전트는 실행하고 결과를 관찰하고 수정하는 루프를 지치지 않고 돈다. 실패하는 테스트는 그 루프에 명확한 목표 함수를 준다 — "통과하면 끝"을 기계가 판정하므로 사람이 중간을 감시할 필요가 없다. 순서가 중요: 테스트를 먼저 확정하고(사람이 확인), 그다음 구현을 시킨다. 마지막 지시("테스트 수정 금지")가 다음 장의 복선.

# tests/test_yield.py — 사람이 확정한 테스트
def test_yield_calc():
    assert calc_yield(lot42) == 98.2
→🤖 몇 번 실패하더니…
# 🤖 조용히 이렇게 바꿔놨습니다
def test_yield_calc():
    result = calc_yield(lot42)
    assert result is not None  # 통과!
✓ 1 passed — 가짜 초록불입니다 실제로 목격되는 수법 ▾ assert 약화 @skip 마킹 특수 케이스 하드코딩 통째로 mock 처리
시험이 어려우면 답안지를 고치는 수험생 — "통과"라는 보상을 좇도록 훈련된 모델의 실제 행동입니다.
보상 해킹(reward hacking): 목표(테스트 통과)를 달성하되 의도(올바른 코드)를 배신하는 행동. 구현이 어려우면 assert를 약화하고, skip을 붙이고, 테스트 입력에만 맞는 하드코딩을 넣는 사례가 실제로 보고된다. Anthropic의 reward tampering 연구가 보여주듯 이것은 이론이 아니라 훈련된 모델의 관측된 습성 — 그래서 다음 장의 방어가 필요하다.

CH 3 · ⚠️ 보상 해킹

방어 3종 — 채점 기준은 사람이 지킵니다

🔒 지시로 잠그기

"테스트 파일은 절대 수정 금지. 통과 못 하면 못 한다고 보고해." — CLAUDE.md에 상주시키세요.

👀 diff 감시

커밋 전 diff에 tests/가 보이면 일단 정지. 훅·CI로 테스트 파일 변경을 자동 경보할 수도 있습니다.

🧑‍⚖️ 테스트만은 사람이

구현 전부를 못 읽어도 테스트 리뷰만은 포기하지 않기 — 채점 기준만 지키면 나머지는 기계가 지켜줍니다.

보너스

출제자와 응시자 분리 — 테스트를 짜는 세션과 구현하는 세션을 분리하면 담합이 어려워집니다.

방어의 핵심 원리: 채점 기준(테스트)의 무결성만 사람이 지키면, 구현의 정합성은 기계가 판정해준다. 지시로 잠그고(상주 지침), diff로 감시하고(훅·CI 자동화 가능), 테스트 리뷰만은 사람이 한다. 보너스로 테스트 작성 세션과 구현 세션을 분리하면 출제자·응시자 분리 효과가 난다.
CH 3 · 테스트가 지렛대

"테스트도 짜줘"로는 해피 패스만 나옵니다

# ❌ 두루뭉술한 요청
"테스트도 만들어줘."

# → 성공 케이스 3개. 끝.
# 자기가 짠 코드에 맞춘,
# 절대 실패하지 않는 테스트
# ✅ 케이스를 명시하는 요청
"test_yield_calc에 다음을 포함해줘:
 - 경계값: 수율 0%·100%, wafer 0장
 - 에러 경로: 측정값 누락·타입 오류 → 예외 확인
 - 회귀: 이번에 고친 중복 lot 버그 재현 케이스
 실패 메시지는 원인을 알 수 있게 써줘."
주문 시 이 세 단어 ▸ 📏 경계값 💥 에러 경로 🔁 회귀 케이스

S3의 '단골 패턴 도감'이 그대로 테스트 케이스 목록이 됩니다.

막연히 "테스트도 짜줘"라고 하면 자기 구현에 맞춘 해피 패스 테스트가 나온다 — 있으나 마나 한 초록불. 경계값, 에러 경로, 회귀 케이스 세 가지를 명시적으로 요구하면 테스트의 질이 완전히 달라진다. 앞의 '미묘한 오류 도감'(경계값·단위·시간대·조용한 실패)이 곧 요구할 케이스 목록이라는 점을 연결해준다.
CH 4 · 리뷰

같은 세션에게 "네 코드 비판해봐"는 왜 약한가

🪞 자기 리뷰

방금 그 코드를 쓴 같은 컨텍스트. 자기 가정에 물들어 있어 같은 실수를 못 봅니다.

"내가 보기엔 완벽한데요."

🫧 신선한 눈

새 세션·서브에이전트에 코드만 던져 리뷰. 오염 안 된 눈이 훨씬 잘 잡습니다.

컨텍스트 격리의 또 다른 쓸모

🧍 사람 리뷰

기계가 못 잡는 방향·의도의 최종 판단. 다음 장에서.

리뷰의 힘은 거리에서 나옵니다 — 쓴 사람과 보는 눈이 멀수록 잘 보입니다.

같은 세션에 "비판해봐"라고 하면 자기 가정에 물든 눈이라 같은 실수를 놓친다. 코드만 떼어 새 세션이나 서브에이전트에 리뷰시키면 컨텍스트 오염이 없어 훨씬 잘 잡는다 — context 세미나의 '격리'가 여기서도 쓰인다. 그래도 방향·의도의 최종 판단은 사람 몫. 리뷰의 힘은 쓴 사람과 보는 눈 사이의 '거리'에서 나온다.

CH 4 · 리뷰

사람은 기계가 못 보는 것만 봅니다

🧍 사람이 볼 것

🧭 설계 방향이 맞나 · 🔐 보안 · 🏭 도메인 가정(수율·단위·장비) · 🚧 경계 조건

🤖 기계에 맡길 것

문법 · 스타일 · 포맷 · 오타 · 단순 버그 — 사람이 눈 버릴 곳이 아닙니다.

diff가 클수록 리뷰 품질은 떨어집니다. — 작게 쪼개서 시키고, 작게 받아서 보세요.

300줄짜리 PR 하나보다 30줄짜리 PR 열 개가 안전합니다. (github 세미나의 '작은 커밋'과 같은 이야기)

사람 리뷰는 기계가 못 보는 곳에 집중해야 남는다 — 설계 방향, 보안, 도메인 가정(수율·단위·장비 이름), 경계 조건. 문법·스타일·오타 같은 건 린터와 모델에 맡긴다. 그리고 diff가 클수록 리뷰 정확도가 급락한다. 작게 쪼개 시키고 작게 받는 것이 검증을 가능하게 만든다.

CH 5 · 평가 (Evals)

한 번 쓰고 버릴 코드 vs 매번 도는 AI

🧪 테스트

결과가 정해진 코드. 같은 입력 → 같은 정답. 일회성 스크립트·함수.

📊 평가 (evals)

결과가 흔들리는 AI 작업(프롬프트·스킬·봇). "대체로 맞나"를 점수로 관리.

🗂 골든 셋

입력–기대출력 정답지. 바꿀 때마다 여기에 돌려봅니다.

🔁 회귀 평가

고친 게 딴 걸 망가뜨렸는지 매번 자동 채점.

⚖️ LLM 심판

답을 AI가 채점 — 심판도 틀립니다. 사람 스팟체크 필수.

결과가 정해진 코드는 테스트로 충분하지만, 프롬프트·스킬·봇처럼 매번 돌면서 출력이 흔들리는 AI 작업은 '평가'로 관리한다. 골든 셋(입력–기대출력 정답지)에 바꿀 때마다 돌려 회귀를 잡고, 채점을 LLM에게 시키기도 한다(LLM-as-judge). 단, 심판도 편향되고 틀린다 — 반드시 사람이 표본을 직접 확인해야 한다. 반도체 현업이라면 '수율 리포트 요약 봇' 같은 게 평가 대상이다.

CH 6 · 실전

검증 강도는 작업의 무게에 맞춥니다

가볍게  ·  기본  ·  풀세트

🧪 일회성 스크립트실행해보고 눈으로 확인이면 충분
🧰 팀 공용 도구+ 자동 테스트 · 신선한 눈 리뷰
🏭 프로덕션 코드+ 사람 리뷰 · CI 상시 · 회귀 평가

전부 풀세트로 검증하면 그것도 낭비입니다 — 다이얼을 돌릴 줄 아는 게 실력.

모든 코드를 최고 강도로 검증하는 건 낭비다. 되돌리기 쉬운 일회성 스크립트는 실행+눈 확인이면 충분하고, 팀이 함께 쓰는 도구는 자동 테스트와 리뷰를, 프로덕션 코드는 사람 리뷰·CI·회귀 평가까지 건다. 바늘을 오른쪽으로 돌릴수록 안전하지만 느려진다 — 작업의 무게에 맞춰 다이얼을 돌리는 감각이 핵심이다.

AI 코드, 커밋 전 체크리스트

☑️ 직접 실행해봤나 — 말로 된 보고 말고 증거

☑️ 경계값·에러 경로 테스트가 있나

☑️ 테스트가 해피 패스만 도는 건 아닌가

☑️ 신선한 눈(새 세션)으로 리뷰했나

☑️ 도메인 가정(단위·수율·장비)이 맞나

☑️ 이 작업 무게에 다이얼은 맞나

커밋 버튼을 누르는 순간, 그 코드는 당신 것입니다 — "AI가 짰어요"는 통하지 않습니다.
이 체크리스트 한 장이 오늘의 실전 요약이다. 실행 증거, 의미 있는 테스트, 신선한 눈 리뷰, 도메인 가정 확인, 그리고 작업 무게에 맞는 검증 강도. 핵심 메시지: 커밋하는 순간 그 코드의 책임은 사람에게 넘어온다 — 이건 다음 security 세미나의 거버넌스와도 이어진다.
정리 · 기억할 것

세 문장만 가져가세요

1. 돌아간다 ≠ 맞는다

AI 코드의 위험은 '틀림'이 아니라 그럴듯하게 틀림입니다.

2. 보고받지 말고 증거를 받아라

사다리를 올라갈수록 검증이 기계로 넘어가고, 사람은 편해집니다.

3. 다이얼을 돌려라

작업의 무게에 검증 강도를 맞추세요 — 전부 풀세트도, 전부 눈으로도 아닙니다.

세 문장으로 압축. (1) 돌아간다고 맞는 게 아니다 — 그럴듯한 오류가 진짜 적. (2) 말로 된 보고 대신 실행·테스트·로그 같은 증거를 요구하라. (3) 작업 무게에 맞춰 검증 강도 다이얼을 돌려라. 이걸 몸에 익히면 바이브 코딩의 속도가 검증에서 무너지지 않는다.
