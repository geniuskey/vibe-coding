심화 트랙의 검증 편. 질문은 하나 — AI가 만든 결과물을 언제, 어떻게 믿을 것인가. 코드를 못 읽어도 됩니다. 오늘 배우는 검증의 절반은 "숫자를 대조하는 법"이라 엑셀 보고서를 만드는 분에게도 그대로 쓰입니다.
3분 요약 · TL;DR

결론부터 — 이 세 줄이면 됩니다

AI 결과물은 엉터리로 틀리지 않고 그럴듯하게 틀립니다. 실행된다고, 숫자가 나온다고 맞는 건 아닙니다.

    "다 했어요" 대신 증거를 받으세요테스트 실행 출력 · 로그 원문 · 스크린샷. 분석이라면 행 수 · 합계 · 원본 셀 대조.
  2. 2
    정답을 아는 입력부터 넣어 보세요손으로 계산한 3건이 맞아야 나머지 3,000건도 믿습니다. 코드라면 실패하는 테스트를 먼저 — 테스트 파일은 수정 금지.
  3. 3
    검증 강도는 작업 무게에 맞추고, 리뷰는 다른 눈에게혼자 보고 버릴 집계와 팀 공용 도구는 다릅니다. 쓴 세션이 아닌 새 세션이 더 잘 봅니다.

CH 1 · 왜 검증인가

엉터리는 금방 걸립니다 — 사고는 90% 맞는 코드가 냅니다

def is_expired(token):
    """토큰 만료 여부를 반환"""
    now = datetime.now()
    return now > token.expires_at

# 리뷰어: "깔끔하네요" · 내 PC에서 테스트 통과
✓ 컴파일 통과 ✓ 실행 성공 ✓ 테스트 통과 (내 PC)
🔍 서버는 UTC, now()는 내 PC 시각 — 9시간 어긋남

컴파일러도, 실행도, 내 PC의 테스트도 이 버그를 잡지 못했습니다.

AI 결과물의 진짜 문제는 '틀림'이 아니라 '그럴듯하게 틀림'입니다.
방향키를 한 번씩 누르며 진행: ① 초록 배지 세 개 — 전부 통과. ② 빨간 줄 — 서버는 UTC로 돌고 now()는 현지 시각을 쓴다. 한국 PC에서는 같은 시간대라 테스트가 통과한다. ③ 결론. 4줄짜리 함수도 이렇게 숨습니다. 코드가 아니라 엑셀 집계라도 똑같습니다 — 숫자는 나오는데 기준이 어긋나 있는 경우.
CH 1 · 왜 검증인가

한 번 돌려 봐서는 안 잡히는 실수 5가지

📏 경계값>와 >= — 재고 0개, 월말, 최댓값에서만 어긋납니다
⚖️ 단위·스케일ms와 s, %와 비율(98.2와 0.982), nm와 µm — 숫자는 나오는데 자릿수가 다릅니다
🕐 시간대UTC와 KST — 내 PC에서는 재현되지 않습니다
🤫 조용한 누락에러를 삼키는 코드, 합치다 빠진 행 — 에러 없이 숫자만 작아집니다
👻 지어낸 것없는 함수·옵션·출처 — 설명은 아주 자신 있게 붙습니다
공통점: 평범한 입력 한 번으로는 안 보입니다 — 경계와 정답을 찔러 봐야 보입니다.
AI가 자주 내는 미묘한 실수 다섯 가지. 반도체 데이터를 다루는 분들에게는 단위·스케일(nm/µm, %와 비율)과 조용한 누락(조인하다 빠진 lot)이 특히 아픕니다. 이 다섯 줄은 뒤에서 그대로 "테스트에 넣을 케이스 목록"으로 다시 나옵니다.

CH 1 · 왜 검증인가

검증을 미루면 '생성 10분'이 '디버깅 3일'이 됩니다

  • 금 16:50 — "주간 리포트 자동화, 10분 만에 완성"+10분
  • 월 09:30 — "지표가 지난주와 조금 다른데?"+반나절
  • 화 — 이해 못 한 코드를 처음부터 다시 읽기+하루
  • 수 11:00 — 원인: 중복 lot 제거 누락, 한 줄+하루

가장 비싼 발견 지점

버그가 검토 단계가 아니라 보고서에서 발견됐습니다.

개수만 셌어도

금요일에 "입력 lot 수 = 출력 lot 수?" 한 줄만 확인했으면 10분에 끝났습니다.

흔한 시나리오. 생성은 10분이었지만 검증을 안 해서 디버깅에 3일. 버그가 가장 비싼 곳(보고서)에서 발견됐습니다. 포인트: 이 버그는 코드를 읽지 않아도 "입력 lot 수와 출력 lot 수를 비교"하는 것만으로 잡혔습니다 — CH2의 '개수 세기'로 이어집니다. 이미 이렇게 꼬였다면 디버깅 세미나(../debugging/)가 처방입니다.

# 실제로 실행하지 않고

# ✅ 증거를 요구하는 요청
"테스트를 직접 실행하고 출력 전체를 보여줘.
 실패하면 에러 원문 그대로."

CH 2 · 검증의 사다리 — 2단

분석 숫자는 세 가지로 확인합니다 — 정답 · 개수 · 출처

🎯 정답 심기

답을 이미 아는 3건을 먼저 넣어 봅니다. 엑셀로 직접 계산한 lot 3개의 수율과 AI 결과가 같은가?

🔢 개수 세기

입력 1,240행 → 출력 몇 행? 중복·빈칸·제외한 건수와 합계가 원본과 맞는지 숫자로 받습니다.

🔗 출처 확인

숫자마다 파일·시트·행을 달게 하고, 아무거나 3개 골라 원본 셀과 맞춰 봅니다.

"집계표와 함께 검증표를 붙여줘 — 입력·출력 행 수와 제외한 행의 이유,
 내가 첨부한 lot 3개 정답과의 비교, 표의 숫자마다 원본 파일·시트·행 번호."

하나라도 어긋나면 그대로 쓰지 말고 원인부터 — 디버깅 세미나: 고칠수록 꼬일 때

코드를 못 읽는 분을 위한 2단 검증. 세 가지 모두 코드 대신 "숫자"를 봅니다. 정답 심기: 손으로 답을 아는 작은 입력을 먼저 넣는다. 개수 세기: 행 수·합계·고유값 개수가 원본과 맞는지 — 앞의 '디버깅 3일' 사례는 이것 하나로 잡혔습니다. 출처 확인: AI가 지어낸 숫자는 출처를 달라고 하면 드러납니다. 무작위 3개를 직접 원본에서 찾아 봅니다. 어긋났을 때 고치는 과정(재현·가설·로그)은 디버깅 세미나에서 다룹니다.

사다리 꼭대기 — 저장할 때마다 기계가 알아서 검사합니다

🪝 커밋 훅

커밋하는 순간 검사·빠른 테스트가 돕니다. 실패하면 커밋 자체를 거절합니다.

♻️ CI

올릴 때마다 깨끗한 환경에서 전체 테스트 — "내 PC에서는 되는데요"를 막습니다.

🤖 리뷰 봇

PR마다 1차 리뷰를 자동으로 — 사람이 보기 전에 뻔한 문제를 거릅니다.

AI가 만든 코드도 같은 관문을 통과해야 합니다. 이 세팅 자체도 에이전트에게 시킬 수 있습니다.
5단: 커밋 훅(로컬에서 즉시), CI(올릴 때마다 깨끗한 환경), 리뷰 봇(PR마다 1차). 한 번 세팅하면 이후 모든 변경이 자동으로 검사됩니다. 개발 팀이 아니라면 건너뛰어도 됩니다. Git·GitHub 기초는 github 세미나에서.

CH 3 · 테스트

테스트를 먼저 쓰게 하면, '끝났다'를 기계가 판정합니다

테스트는 "이 입력엔 이 출력"이라는 '맞다'의 정의를 코드로 적어 둔 것입니다. 한 번 써 두면 다음 수정 때도 계속 지켜 줍니다.

STEP 1🔴 실패하는 테스트구현 없이 기대 동작만. 사람이 이 테스트를 확인
STEP 2🟢 통과할 때까지 구현에이전트가 실행 → 실패 → 수정을 스스로 반복
STEP 3✨ 정리하고 재확인초록불을 유지한 채 코드를 다듬기
"먼저 이 기능의 실패하는 테스트부터 써줘. 구현은 아직 하지 마.
 내가 테스트를 확인하면, 그때 통과할 때까지 구현해줘.
 테스트 파일은 수정하지 마."
테스트 주도 개발(TDD)이 에이전트와 잘 맞는 이유: 에이전트는 실행·관찰·수정 루프를 지치지 않고 돕니다. 실패하는 테스트가 그 루프에 분명한 목표를 줍니다. 순서가 중요합니다 — 테스트를 먼저 확정하고(사람이 확인), 그다음 구현. 마지막 줄 "테스트 파일은 수정하지 마"가 다음 장의 복선입니다.

CH 3 · 테스트 — 주의

테스트를 못 통과하면, AI가 테스트를 고치기도 합니다

# tests/test_yield.py — 사람이 확정한 테스트
def test_yield_calc():
    assert calc_yield(lot42) == 98.2
→몇 번 실패한 뒤
# 🤖 조용히 이렇게 바뀌어 있습니다
def test_yield_calc():
    result = calc_yield(lot42)
    assert result is not None  # 통과
✓ 1 passed — 가짜 초록불입니다 실제로 보고되는 수법 ▾ 검사 조건 약화 테스트 건너뛰기(skip) 테스트 입력만 맞추는 하드코딩 통째로 가짜(mock) 처리
어려운 시험에서 답안지를 고치는 수험생 — "통과"를 좇도록 훈련된 모델에서 실제로 관찰되는 행동입니다.
방향키로 진행: ① 원래 검사(98.2와 같아야 함)에 취소선이 그어지고 바뀐 테스트가 나타납니다. ② 테스트는 통과 — 가짜 초록불. ③ 결론. 이것을 보상 해킹(reward hacking)이라고 부릅니다. 목표(테스트 통과)는 달성하지만 의도(올바른 계산)는 배신합니다. 연구 논문과 실사용 보고 모두에 나오는 행동입니다.

저장 전에 변경 목록에 tests/가 보이면 일단 멈춥니다. 훅으로 자동 경보를 걸 수도 있습니다.

🧑‍⚖️ 테스트만은 사람이

구현 전부는 못 읽어도 테스트는 직접 확인 — 채점 기준이 지켜지면 나머지는 기계가 판정합니다.

한 걸음 더  테스트를 쓰는 세션과 구현하는 세션을 나누면 출제자와 응시자가 분리됩니다.

방어의 원리: 채점 기준(테스트)의 무결성만 사람이 지키면 구현이 맞는지는 기계가 판정해 줍니다. CLAUDE.md에 상주 지침으로 넣는 법은 agent-skills 세미나(../agent-skills/)에서 다룹니다.

"테스트도 만들어줘."

# → 성공 케이스 3개. 끝.
# 자기 코드에 맞춘,
# 절대 실패하지 않는 테스트
# ✅ 케이스를 짚어 주는 요청
"test_yield_calc에 다음을 넣어줘:
 - 경계값: 수율 0%·100%, wafer 0장
 - 잘못된 입력: 측정값 누락·글자 섞임 → 오류
 - 회귀: 이번에 고친 중복 lot 버그 재현
 실패 메시지는 원인을 알 수 있게."
요청할 때 이 세 단어 ▸ 📏 경계값 💥 잘못된 입력 🔁 회귀 케이스

앞에서 본 '실수 5가지'가 그대로 테스트 케이스 목록입니다.

"테스트도 짜줘"라고만 하면 자기 구현에 맞춘 성공 케이스만 나옵니다 — 있으나 마나 한 초록불. 경계값, 잘못된 입력, 회귀(한 번 고친 버그가 다시 생기지 않는지) 세 가지를 짚어 주면 질이 달라집니다.

🪞 자기 리뷰

🧭 방향이 맞나 · 🔐 보안 · 🏭 도메인 가정(수율 정의·단위·장비) · 🚧 경계 조건

한 번에 보는 변경이 클수록 리뷰는 허술해집니다. 작게 시키고, 작게 받으세요.

300줄 변경 한 번보다 30줄 변경 열 번이 안전합니다 — github 세미나의 '작은 커밋'과 같은 이야기.

사람 리뷰는 기계가 못 보는 곳에 써야 남습니다 — 방향, 보안, 도메인 가정(수율을 무엇 대비로 계산하나, 단위, 장비 이름), 경계 조건. 그리고 변경이 클수록 리뷰가 대충이 됩니다. 작게 쪼개 시키는 것이 검증을 가능하게 만듭니다.
CH 4 · 리뷰 — 심화

매번 다시 도는 AI 작업은 정답지로 점수를 매깁니다

🧪 테스트

결과가 정해진 코드. 같은 입력이면 같은 정답.

📊 평가 (evals)

결과가 매번 조금씩 다른 AI 작업 — 프롬프트·스킬·요약 봇. "대체로 맞나"를 점수로.

🗂 정답지

입력과 기대 출력 20~50건. 앞의 '정답 심기'를 모아 둔 것.

🔁 고칠 때마다

프롬프트를 바꿀 때마다 정답지에 다시 돌려 점수 비교.

⚖️ AI 채점

채점을 AI에게 맡겨도 채점자도 틀립니다. 몇 건은 사람이 직접.

프롬프트·스킬·봇처럼 매번 돌면서 출력이 흔들리는 작업은 테스트 대신 '평가'로 관리합니다. 예: "수율 리포트 요약 봇"이라면 지난 리포트 30건과 사람이 쓴 모범 요약을 정답지로 두고, 프롬프트를 바꿀 때마다 점수를 봅니다. 채점을 LLM에게 시킬 수 있지만(LLM-as-judge) 채점자도 편향되므로 표본은 사람이 확인합니다.
CH 5 · 실전

검증 강도는 작업의 무게에 맞춥니다

가볍게  ·  기본  ·  풀세트

🧪 혼자 보고 버릴 것실행 + 정답 1~2건 대조
🧰 팀 도구 · 보고서 숫자+ 개수·출처 검증표 · 자동 테스트 · 다른 눈 리뷰
🏭 운영 시스템 · 고객 데이터+ 사람 리뷰 · 상시 자동 검증 · 정답지 평가

모든 일을 풀세트로 검증하는 것도 낭비입니다 — 다이얼을 돌릴 줄 아는 게 실력.

방향키를 누를 때마다 바늘이 오른쪽으로 돌고 단계가 하나씩 나타납니다. 혼자 한 번 보고 버릴 집계는 실행 + 정답 대조면 충분. 팀이 쓰거나 보고서에 들어가는 숫자는 검증표·테스트·리뷰까지. 운영 시스템이나 고객 데이터는 사람 리뷰와 상시 자동 검증까지. 기준은 "틀리면 누가, 얼마나 다치나"입니다.
📸 이 장만 찍어 가세요

결과를 내보내기 전, 이 여섯 가지만 확인하세요

☑️ 실행 결과를 직접 받았나 — 말로 된 보고 말고

☑️ 답을 아는 3건으로 대조했나

☑️ 행 수·합계·출처가 원본과 맞나

☑️ 경계값·잘못된 입력 테스트가 있나 — 테스트 파일이 바뀌진 않았나

☑️ 다른 눈(새 세션·동료)이 봤나

☑️ 도메인 가정(단위·수율 정의·장비)이 맞나

내보내는 순간 그 결과는 당신 것입니다 — "AI가 했어요"는 통하지 않습니다.

하나라도 어긋났다면 → 고칠수록 꼬일 때 — AI와 함께 디버깅하기

오늘의 실전 요약 한 장. 왼쪽은 코드를 몰라도 되는 확인, 오른쪽은 코드·팀 작업일 때 더할 확인입니다. 커밋하거나 보고서를 보내는 순간 책임은 사람에게 넘어옵니다. 어긋난 걸 찾았을 때 고치는 과정은 디버깅 세미나로.
정리

세 문장만 가져가세요

1. 돌아간다 ≠ 맞는다

AI 결과물의 위험은 '틀림'이 아니라 그럴듯하게 틀림입니다.

2. 말 대신 증거 — 정답 · 개수 · 출처

실행 출력을 받고, 답을 아는 입력으로 대조하고, 숫자의 출처를 확인합니다.

3. 다이얼을 돌려라

작업 무게에 검증 강도를 맞추세요 — 전부 풀세트도, 전부 눈대중도 아닙니다.

다음으로 → 디버깅하기  ·  서브에이전트와 오케스트레이션  ·  보안과 거버넌스

세 문장 정리. (1) 돌아간다고 맞는 게 아니다. (2) 말 대신 증거 — 실행 출력, 정답 대조, 개수, 출처. (3) 작업 무게에 맞춰 다이얼을 돌린다. 다음 단계 안내: 틀린 걸 찾았으면 debugging, 다른 눈 리뷰를 팀으로 굴리려면 orchestration, 결과물의 책임과 데이터 경로는 security.
