CH 1 · 왜 헛도나

같은 에러가 세 번 나왔다면, 모자란 건 AI의 실력이 아니라 정보입니다

AI가 받은 것

  • "에러 나. 고쳐 줘" — 한 줄
  • 에러 메시지 원문
  • 언제, 무엇을 했을 때 나는지
  • 어떤 파일·데이터로 했는지
  • 원래 기대한 결과가 무엇인지

그래서 AI가 하는 일

가장 흔한 원인을 짐작해서 고칩니다.

짐작이 빗나가도 결과를 직접 확인하지 않았으니 "수정했습니다"라고 보고합니다.

다음 요청에서는 또 다른 짐작을 그 위에 얹습니다.

의사에게 "아파요"만 말하면 처방도 짐작이 됩니다. 어디가, 언제부터, 어떻게 아픈지를 말해야 합니다.
AI가 무능해서 헛도는 게 아니다. 왼쪽 목록에서 AI가 실제로 받은 건 한 줄뿐이다. 정보가 없으면 AI는 "이런 에러는 보통 이것 때문"이라는 짐작으로 고친다. 짐작이 맞으면 다행, 빗나가면 그 수정이 코드에 남는다. 청중에게 묻기: 최근에 "고쳐 줘"만 보낸 적 있는지.
CH 1 · 왜 헛도나

헛도는 이유는 셋 — 정보 부족, 대화 오염, 추측 수정의 누적

🩺 원인 정보가 없다

증상만 받으면 AI는 확인하지 않고 고칩니다.

처방 → 재현 방법·에러 원문·기대 vs 실제를 준다

🌫 대화가 오염됐다

실패한 시도와 틀린 가설이 대화에 쌓이고, AI는 그것을 사실처럼 다시 참고합니다.

처방 → 요약을 들고 새 세션으로

🧱 추측 수정이 쌓였다

빗나간 수정이 지워지지 않고 남아, 원래 버그 위에 새 버그가 덮입니다. "고칠수록 꼬인다"의 정체입니다.

처방 → 되돌리고, 한 번에 하나씩

세 원인 모두 "더 세게 부탁하기"로는 풀리지 않습니다. 주는 정보, 대화의 판, 수정의 순서를 바꿔야 합니다.
세 가지를 구분하면 처방이 갈린다. (1) 정보 부족 → 다음 장의 디버깅 루프. (2) 대화 오염 → 새 세션 리셋. 원리는 context 덱에서 자세히. (3) 추측 수정 누적 → 되돌리기 + 한 번에 하나. 특히 (3)이 비개발자가 가장 많이 빠지는 함정: 고쳐 달라고 할 때마다 코드가 조금씩 더 이상해진다.

"고쳐 줘"는 넷째 단계입니다 — 앞의 셋을 먼저

① 재현다시 일으키기언제 · 무엇을 하면 · 무엇이 나오나
② 전달정확히 말하기에러 원문 · 스크린샷 · 기대 vs 실제
③ 가설원인 후보 받기후보 3개와 각각의 확인 방법
④ 하나씩하나만 고치기확인된 원인 하나, 다른 곳은 그대로
⑤ 확인같은 절차로 재확인①을 그대로 다시 — 되면 커밋
안 되면 그 수정은 되돌리고 ③으로
①–③을 건너뛰고 ④부터 시키면, 그것이 바로 추측 수정입니다.
오늘의 뼈대. 다섯 단계 이름만 기억하면 된다: 재현 · 전달 · 가설 · 하나씩 · 확인. 대부분의 사람은 ④부터 시작한다. 앞의 세 단계는 AI가 짐작하지 않고 원인을 고르게 만드는 단계다. ⑤에서 안 되면 그 수정은 남겨 두지 말고 되돌린 뒤 ③(다른 후보)으로 돌아간다 — 이게 "꼬임"을 막는 핵심. 다음 네 장에서 단계마다 실제 문장을 본다.

가끔이라면 "날 때와 안 날 때 무엇이 달랐나"가 가장 큰 단서입니다. 파일, 시간, PC, 클릭 순서를 비교하세요.

재현이 안 되면 고쳤는지도 모릅니다

이 문장은 ⑤ 확인 단계에서 그대로 다시 씁니다. 그래서 처음에 적어 두는 겁니다.

재현 문장은 세 칸 채우기다. 예시처럼 구체적으로 — "가끔 안 돼요"가 아니라 "이 파일로, 이 순서로 하면, 이게 나온다". 재현 문장이 있으면 AI도 같은 절차로 직접 실행해 볼 수 있다. 또 ⑤에서 "고쳐졌는지"를 판정하는 기준이 된다.

② 전달 — 해석하지 말고 원문, 그리고 "기대 vs 실제"

📸 화면 문제는 스크린샷을 함께 — 말로 설명하기 어려운 어긋남이 그대로 전달됩니다.

3월 행만 비고 칸에 쉼표가 들어 있어 — 관계있을지도 몰라.
스크린샷 첨부할게. 아직 고치지 말고 원인부터 같이 보자.
오른쪽 카드의 구조: 재현 문장 + 기대 + 실제 + 눈치챈 차이 + 스크린샷. "에러 메시지는 없음"도 중요한 정보다. 비개발자가 흔히 하는 실수는 에러를 자기 말로 바꿔 전달하는 것 — "뭔가 파일 문제래요". 원문 그대로가 훨씬 낫다. 에러 원문에 실데이터·경로 속 개인정보·키가 섞여 있으면 지우고 붙인다(보안 약속 1·2).

③ 가설 — 고치기 전에 "원인 후보 3개와 확인 방법"을 받습니다

아직 고치지 마. 원인 후보 3개를 가능성 순으로 적고,
각각을 어떻게 확인할 수 있는지 알려 줘.

확인도 AI에게 맡길 수 있습니다 — "1번부터 확인해서 결과만 보여 줘".

결과를 보고 원인이 확정된 후보만 ④로 넘깁니다.

● 원인 후보 (가능성 순)

1. 비고 칸의 쉼표 때문에 3월 행의 칸이 밀림
   확인: 3월 행만 남긴 파일로 실행해 칸 수 출력

2. 3월 날짜 형식이 달라 읽을 때 빠짐
   확인: 읽은 직후 날짜 값을 그대로 출력

3. 그래프 필터 조건이 3월을 제외
   확인: 필터 전·후 행 수를 비교
후보마다 확인 방법이 붙어 있으면, 짐작이 아니라 증거로 원인을 고를 수 있습니다.
이 덱에서 단 하나만 가져간다면 이 문장: "아직 고치지 마. 원인 후보 3개와 확인 방법." "고치지 마"가 핵심이다. 이 말이 없으면 AI는 후보를 말하면서 동시에 1번을 고쳐 버린다. 후보가 셋이면 첫 짐작에 매달리지 않게 된다. 확인 방법은 대개 로그 출력이나 작은 입력 — 뒤에서 다시 다룬다.
① 재현② 전달③ 가설④ 하나씩⑤ 확인

④ 하나만 고치고, ⑤ 처음 재현 절차 그대로 확인합니다

④ 한 번에 하나

세 군데를 한꺼번에 고치면 무엇이 효과였는지, 새 문제가 어디서 왔는지 알 수 없습니다.

⑤ 같은 절차로 확인

"수정했습니다"는 보고일 뿐입니다. ①의 재현 문장대로 다시 해 보고 눈으로 확인합니다.

❌ 그대로다 → 그 수정은 되돌리고 ③의 다음 후보로

증거를 받는 법은 → ../verification/

④에서 "다른 곳은 건드리지 마"와 "바꾼 내용을 3줄로"를 꼭 붙인다. 바꾼 내용을 알아야 되돌릴 수 있다. ⑤에서 실패한 수정을 남겨 두면 추측 수정이 쌓인다 — 이게 "고칠수록 꼬인다"의 원인이었다. 안 되면 되돌린다. 되면 바로 커밋. github 덱의 세이브 포인트와 연결된다.
CH 3 · 루프가 안 돌 때

세 번 헛돌면 같은 요청을 반복하지 말고, 판을 바꿉니다

🪵로그 심기보이지 않던 중간값을 화면에 꺼낸다원인이 안 보일 때
✂️입력 줄이기되는 데이터와 안 되는 데이터를 비교한다특정 데이터에서만 날 때
↩️되돌리고 다른 접근쌓인 추측 수정을 걷어낸다고칠수록 꼬일 때
🧼새 세션 리셋요약 파일만 들고 깨끗한 대화로같은 실수를 반복할 때
🧠더 깊이 생각고치지 말고 원인 분석만 맡긴다위를 다 해도 막힐 때
기준은 단순합니다 — 같은 증상으로 세 번 고쳤는데 그대로라면, 네 번째 "고쳐 줘"는 보내지 않습니다.
세 번은 엄격한 규칙이 아니라 손에 잡히는 기준이다. 세 번째에도 같은 증상이면 지금 판에는 원인을 찾을 정보가 없다는 뜻. 다섯 도구는 대략 왼쪽부터 쓴다. 각 도구 아래 초록 글씨가 "언제 꺼내나".
CH 3 · 🪵 로그 심기

로그를 심으면, 어디서부터 틀어지는지 눈으로 보입니다

로그 = 프로그램이 일하는 중간중간 남기는 메모. 단계마다 값을 찍어 두면, 처음으로 값이 이상해지는 지점이 원인 근처입니다.

💬 이렇게 요청
고치지 말고, 파일을 읽은 직후 · 계산 직전 · 화면에 그리기 직전에 값을 출력하는 로그를 넣어 줘. 실행 결과를 보고 어디서 틀어지는지 짚어 줘.

로그가 나오는 곳 — 웹페이지는 F12 → Console, 파이썬은 터미널. 원인을 찾은 뒤에는 "디버깅용 로그는 지워 줘".

상대 경로는 어디서 실행했느냐에 따라 가리키는 곳이 바뀝니다. "파일이 없다"는 에러의 단골 원인입니다.

피할 폴더 이름 · 한글 · 공백C:\Users\김철수\내 문서\2026 보고\
작업 폴더는 영문 · 공백 없이C:\work\yield-report\

어떤 도구는 공백에서 경로를 끊고, 어떤 도구는 한글 경로를 못 읽습니다. 공백이 있으면 경로를 "따옴표"로 감쌉니다.

Windows는 \, Mac은 / 로 폴더를 나눕니다. 다른 PC에서 받은 코드가 "파일이 없다"고 하면 이것부터 의심합니다.
AI가 가장 자주 쓰는 용어가 경로다. 절대 경로는 집 주소 전체, 상대 경로는 "여기서 두 블록 옆" 같은 설명. 상대 경로는 실행 위치에 따라 의미가 바뀐다. 터미널을 다른 폴더에서 열고 실행하면 같은 코드가 파일을 못 찾는다. 사내 PC는 사용자 폴더 이름이 한글이거나 "내 문서"처럼 공백이 있는 경우가 많다 — 작업 폴더를 C:\work 아래에 따로 만들라고 권한다.
CH 4 · AI의 말 알아듣기

이 네 단어만 알면 에러 메시지의 절반이 읽힙니다

📦 패키지 · 모듈 module

남이 만들어 둔 부품. No module named … 는 "그 부품이 안 깔렸다", 또는 "깐 곳과 실행하는 파이썬이 다르다".

🔌 localhost · 포트 :8000

localhost는 "내 컴퓨터 자신", 포트는 그 안의 문 번호입니다.

이 주소는 터미널에서 서버가 돌고 있는 동안만 열립니다. 터미널을 닫으면 서버도 꺼지고, 다른 사람 PC에서는 열리지 않습니다.

🖥 콘솔 console

프로그램이 에러와 로그를 적는 창. 웹페이지는 F12 → Console 탭, 파이썬은 실행한 터미널 그 자체입니다.

🔤 인코딩 encoding

글자를 숫자로 저장하는 규칙. 한글 Windows 엑셀의 CSV는 흔히 CP949, 요즘 도구의 기본은 UTF-8.

규칙이 다르게 읽으면 �� · ÇÑ±Û 처럼 깨집니다.

용어를 외우자는 게 아니라, AI가 "포트가 사용 중이에요"라고 할 때 무슨 뜻인지 감을 잡자는 것. localhost가 특히 많이 헷갈린다: AI가 "http://localhost:8000 에서 확인하세요"라고 해서 열었는데 다음 날 안 열린다 → 서버를 띄운 터미널을 닫았기 때문. 팀원에게 localhost 주소를 보내도 열리지 않는다. 공유는 github 덱의 GitHub Pages 배포로.

📁 파일을 찾을 수 없음 FileNotFoundError · No such file or directory · ERR_FILE_NOT_FOUND

원인상대 경로의 기준 폴더가 다름 · 오타 · 한글·공백 폴더

처방"현재 실행 폴더와 파일의 실제 위치를 둘 다 출력해서 비교해 줘"

에러 이름을 해석할 필요는 없다 — 카드에서 모양이 비슷한 것을 찾고 처방 문장을 함께 붙이면 된다. 한글 깨짐: 한글 Windows의 엑셀에서 "CSV (쉼표로 분리)"로 저장하면 보통 CP949다. 엑셀에는 "CSV UTF-8" 저장 옵션도 따로 있다. 모듈 없음: PC에 파이썬이 여러 개 깔린 경우가 흔하다. 사내망이면 설치 자체가 프록시에 막힐 수 있다 → 다음 장. 설치 단계의 에러(claude 명령을 못 찾음 등)는 setup 덱 TOP 5에 있다.

  • 골라도 아무 반응이 없다 → 콘솔의 첫 빨간 줄 원문을 그대로 붙인다
  • 글자가 깨진다 → "엑셀에서 내보낸 CSV야" 한 줄을 보탠다
  • 몇 행만 숫자가 이상하다 → 이상한 행과 멀쩡한 행을 한 줄씩 붙여 "뭐가 달라?"
  • 세 번 헛돈다 → debug-notes.md 로 요약하고 새 세션
완료 숫자를 AI에게 미리 알려 주지 마세요. "92.8%가 나오게 해 줘"는 답을 맞추는 코드를 부를 수 있습니다.
정답 값(92.8%, 저수율 3개)은 사람이 확인하는 기준이다. AI에게 목표 숫자를 주면 값을 억지로 맞추는 수정을 할 수 있다 — verification 덱의 보상 해킹 이야기와 같은 맥락. 막힘 대처 네 줄은 각각 이 덱의 도구와 짝이다: 원문 전달, 정보 보태기, 입력 줄이기(행 비교), 새 세션 리셋. 시간이 남으면 보너스: debug-notes.md 정리 → 다음에 같은 류의 문제가 나면 이 파일을 먼저 읽히면 된다. 해설: (1) 스크립트 경로를 csv.js 로, (2) readAsText(file, 'EUC-KR') 등 인코딩 지정, (3) 따옴표 안 쉼표를 처리하는 CSV 파싱 + 숫자 속 쉼표 제거.

[파일]로 [동작]을 하면 [결과]가 나와. 기대: … / 실제: … / 에러 원문: (붙여넣기)
③ 가설 먼저
아직 고치지 마. 원인 후보 3개를 가능성 순으로, 각각 확인 방법과 함께 알려 줘.
④ 하나만
1번 원인만 고쳐 줘. 다른 곳은 건드리지 말고, 바꾼 내용을 3줄로 알려 줘.
🪵 로그
고치지 말고, 단계마다 값을 출력하는 로그를 넣어 줘. 실행 결과로 어디서 틀어지는지 짚어 줘.
✂️ 입력 줄이기
되는 데이터와 안 되는 데이터를 가장 작게 줄여서, 둘이 무엇이 다른지 찾아 줘.
🧼 리셋 전 요약
지금까지를 debug-notes.md 로 정리해 줘: 증상 · 재현 방법 · 시도와 결과 · 남은 가설.
🧠 분석만
코드는 고치지 마. 지금까지의 수정이 왜 실패했는지와 근본 원인, 그걸 확인할 방법만 분석해 줘.
카드마다 오른쪽 위 복사 버튼이 있다. 루프 순서(①~④)와 판을 바꾸는 도구 순서대로 배치했다. 공통점: 대부분 "고치지 마"로 시작한다. 관찰·분석과 수정을 분리하는 것이 이 덱 전체의 요령.
📸 이 장표만 찍어 가세요

같은 에러가 두 번 나면 — 이 순서로

  • 재현 문장 — 언제 · 무엇을 하면 · 무엇이 나오나
  • 에러 원문 전체 + 스크린샷 + 기대 vs 실제
  • "아직 고치지 마. 원인 후보 3개와 확인 방법"
  • 한 번에 하나 → 같은 절차로 재확인 → 되면 커밋, 안 되면 되돌리기
  • 세 번 헛돌면 판 바꾸기 — 로그 · 입력 줄이기 · 되돌리기 · 새 세션 · 깊이 올리기
