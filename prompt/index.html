CH 1 · 원리

AI는 적힌 것만 압니다 — 빈칸은 평균으로 채웁니다

🔮 AI는 독심술사가 아닙니다

AI는 적힌 것만 알 수 있습니다. 내 머릿속의 "당연한 것"(누가 볼 자료인지, 어떤 형식인지, 뭐가 중요한지)은 적지 않으면 존재하지 않습니다.

🎲 빈칸은 '평균'으로 채워집니다

지시가 비면 AI는 세상에서 가장 흔한 답을 만듭니다. 무난하지만 내 상황엔 안 맞는 결과 — "요약해줘"가 매번 다른 이유입니다.

그래서 프롬프트의 본질은 화려한 문장이 아니라 — 내 머릿속 정보를 AI의 책상 위로 옮기는 일입니다.

이 "책상"의 정체(컨텍스트 창)는 컨텍스트 세미나에서 깊게 다룹니다.

원리는 이 한 장으로 끝 — "빈칸은 평균으로 채워진다"는 표현이 오늘 전체를 관통한다. making-slides 세미나의 '평균으로의 회귀'와 같은 개념. 이후 슬라이드는 전부 "빈칸을 어떻게 채우나"의 기술.
CH 1 · 원리

신입에게 일 시키는 법을 이미 알고 계십니다

🧑‍💼 유능한 선배의 업무 지시
"김 프로, 다음 주 고객사 미팅용으로
이 데이터 정리 좀 부탁해요.
지난번 A사 보고서 형식이 좋았으니 그대로,
결론 페이지가 제일 중요하고,
수요일까지 초안이면 됩니다.
막히면 중간에 물어봐요."

이 지시에는 이미 전부 들어 있습니다:

  • 🎯 목표 — 미팅용 데이터 정리
  • 🗺️ 맥락 — 다음 주 고객사 미팅
  • 📏 제약 — 수요일까지 초안
  • 🃏 예시 — 지난번 A사 보고서처럼
  • ⭐ 우선순위 — 결론 페이지가 핵심
  • 🙋 질문 허용 — 막히면 물어봐요
프롬프트 엔지니어링 = 이 능력을 AI에게 켜는 것. 새로 배울 것이 생각보다 적습니다.
심리 장벽 제거 슬라이드. "프롬프트 엔지니어링"이라는 말의 위압감을 없앤다 — 직장인은 이미 위임의 달인이고, 상대가 사람에서 AI로 바뀌었을 뿐.

단, 완벽한 첫 문장을 쓰려고 5분 고민하지 마세요. 짧게 시작하고 대화로 채우는 것이 더 빠릅니다 — CH 3에서.

워크숍의 '좋은 지시 3요소'와 동일한 프레임 — 여기가 원전이 되도록 조금 더 깊게. 3칸을 다 채우는 게 목적이 아니라, 결과가 이상할 때 "어느 칸이 비었나"를 진단하는 도구로 쓰라고 안내.
CH 2 · 패턴

복사해서 바로 쓰는 패턴 8가지

① 계획 먼저

일 시키기 전에 계획부터 받기

② 형식 지정

결과물의 모양을 정해주기

③ 번호 목록

여러 요청은 번호로 쪼개기

④ 예시 주기

말 대신 견본으로 보여주기

⑤ 역할·독자

누구를 위한 결과물인지

⑥ 스스로 검증

만든 것을 직접 확인시키기

⑦ 모르면 묻기

추측 대신 질문하게 하기

⑧ 쪼개기

큰 일은 단계로 나눠 시키기

전부 외울 필요 없습니다 — 마지막에 치트시트 한 장으로 드립니다. 지금은 "이런 게 있구나"만.

패턴 파트 목차. 각 패턴은 한 장씩 — 구조는 동일하게 (왜 먹히나 한 줄 + 복사용 프롬프트 + 미니 팁). 시간이 없으면 ①②④⑥만 하고 나머지는 치트시트로 넘겨도 된다.
PATTERN 01

계획부터 받으면, 어긋남을 만들기 전에 잡습니다

왜 먹히나 방향이 어긋난 채 완성되면 되돌리기 비쌉니다. 계획 단계에서는 한 줄만 고치면 됩니다.
💬 복사해서 쓰세요
바로 만들지 말고, 먼저 어떻게 만들 계획인지
단계별로 보여줘. 내가 확인하면 시작하자.

계획이 나오면 어긋난 부분만 짚으면 됩니다 — "2번은 필요 없어", "결과는 엑셀 말고 웹페이지로".

💡 언제 쓰나: 오래 걸릴 일, 파일을 여러 개 만드는 일, 원하는 것이 나도 아직 흐릿한 일. Claude Code에서는 플랜 모드가 같은 일을 합니다.

여덟 패턴 중 효과가 가장 크다. 계획 없이 시작해 산으로 간 경험담을 하나 곁들이면 좋다. 플랜 모드(Shift+Tab) 조작은 setup 덱에서 다룬다 — 여기서는 "계획을 받고, 어긋난 줄만 고친다"는 습관만.
PATTERN 02

형식을 정해 주면, 내용에만 집중합니다

왜 먹히나 형식이 비면 AI가 형식까지 창작합니다. 모양을 못 박으면 내용에만 집중시킬 수 있습니다.
💬 문서 작업이라면
결론 먼저 3줄 → 근거는 표로
(항목/수치/출처 열) → 마지막에
리스크 2가지. A4 한 장 이내로.
💬 코딩 작업이라면
HTML 파일 하나로 만들어줘.
설치나 별도 프로그램 없이
더블클릭으로 열리게.

자주 쓰는 형식 표현: 표로 5줄 이내 번호 목록으로 파일 하나로 전문용어 없이

"결론 먼저"는 보고 문화가 있는 조직에서 특히 반응이 좋다. 형식이 정해져 있으면 빠진 것이 한눈에 보여서 검수도 쉬워진다.
PATTERN 03

요청이 여러 개면 번호를 붙입니다

왜 먹히나 줄글에 섞인 요청은 누락됩니다. 번호가 있으면 AI도 하나씩 처리하고, 나도 하나씩 검수할 수 있습니다.
😕 요청이 문장에 매몰
제목 좀 키우고 색은 파란 계열로 바꾸고
아 그리고 버튼이 안 눌리는 것 같던데
확인해주고 표도 정렬 좀…
→
😎 하나씩 짚을 수 있음
다음 4가지를 고쳐줘:
1. 제목 글자 크게
2. 전체 색을 파란 계열로
3. 저장 버튼이 안 눌리는 문제
4. 표를 날짜순 정렬

💡 보너스: 끝에 "다 되면 각 번호별로 뭘 했는지 알려줘"를 붙이면 검수가 배로 쉬워집니다.

번호 목록은 사람끼리 일할 때도 쓰는 기술이라 저항 없이 받아들여진다. "번호별로 뭘 했는지 알려줘"까지 붙이게 할 것.
PATTERN 04

설명 대신 견본 하나를 붙입니다

왜 먹히나 형식·톤·스타일은 말로 다 적기 어렵습니다. 견본을 주면 AI가 규칙을 스스로 뽑아냅니다.
💬 복사해서 쓰세요
아래 예시와 같은 형식·톤으로 이번 주 것도 만들어줘:

[지난주에 잘 뽑힌 결과물 붙여넣기]

📄 주간보고 — 지난주 보고를 붙여넣고 "이 형식 그대로"

📧 메일 — 잘 쓴 메일 하나를 견본으로 "이 톤으로"

🎨 화면 — 마음에 든 페이지·스크린샷을 붙이고 "이 스타일로"

⚠️ 견본에 기밀·실데이터가 있으면 지우거나 가린 뒤 붙입니다. 견본 하나로 디자인 전체를 옮기는 응용은 슬라이드 덱의 "레퍼런스 앵커링".

few-shot 프롬프팅을 비개발자 언어로. "여러분에게는 이미 견본이 있다(지난주에 만든 것)"가 실전 포인트. 견본을 붙일 때 기밀·실데이터는 지우거나 가린다 — 사내 승인 도구가 아니면 애초에 넣지 않는다.
PATTERN 05

읽을 사람을 정하면 어휘와 깊이가 맞춰집니다

왜 먹히나 같은 내용도 독자에 따라 완전히 다른 글이 됩니다. 독자를 지정하면 어휘·깊이·톤이 통째로 조정됩니다.
💬 독자 지정
이 장비 이상 분석 결과를
비엔지니어인 구매팀이 이해할 수 있게
설명해줘. 전문용어에는 한 줄 설명을 붙여서.
💬 역할 지정
너는 깐깐한 품질 감사관이야.
이 보고서에서 근거가 약한 주장을
전부 찾아서 지적해줘.

💡 역할 지정의 실전 최강 활용: 반대 역할을 시키는 것 — "내 계획의 허점을 공격해봐", "이 메일을 받는 상대방 입장에서 읽고 기분 나쁠 부분을 짚어줘".

"너는 ~야" 역할극이 미신처럼 소비되는 것을 교정 — 마법이 아니라 어휘·깊이·관점의 조정 장치. 반대 역할(레드팀) 활용이 이 패턴의 실전 가치.
PATTERN 06

"다 됐습니다"를 믿으려면 확인까지 시킵니다

왜 먹히나 AI는 확인 없이 "다 됐습니다"라고 말하기도 합니다. 확인 절차를 지시에 넣으면 오류가 내 앞에 오기 전에 걸러집니다.
💬 코딩 작업이라면
다 만들면 직접 실행해서
에러가 없는지 확인하고,
확인한 결과를 보여줘.
💬 데이터 작업이라면
집계가 끝나면 원본 행 수와
결과 합계가 맞는지 교차 확인하고,
확인 과정을 함께 보여줘.
⚠️ AI의 자체 확인은 1차 필터입니다. 숫자·사실의 최종 확인은 사람 몫 — 답을 아는 값 하나를 넣어 보는 "정답 심기"가 가장 확실합니다. 검증 덱 ↗
워크숍의 검증 습관(정답 심기·개수 세기·아는 값 넣기)과 연결. 자체 확인을 맹신하지 않도록 균형을 잡아 준다. 더 깊은 내용(검증의 사다리·테스트)은 verification 덱.
PATTERN 07

모르면 묻게 하면, 추측 대신 질문이 옵니다

왜 먹히나 AI는 모호한 지시를 받으면 질문 대신 추측합니다. 질문을 명시적으로 허용하면 추측 대신 확인하고 시작합니다.
💬 복사해서 쓰세요 — 긴 지시 끝에 한 줄
시작하기 전에, 불명확하거나 내가 정해줘야 할 것이
있으면 먼저 질문해줘.

덤으로, AI의 질문을 보면 내 지시의 빈칸이 보입니다. "아, 이걸 안 정해 줬구나" — 세 칸 중 어디가 비었는지 알려 주는 셈입니다.

💡 언제 쓰나: 요구사항이 복잡할 때, 내 머릿속도 아직 정리가 덜 됐을 때, 다시 만들기 아까운 큰 결과물일 때.

추측 vs 질문의 차이를 신입 비유로: 좋은 신입은 애매하면 물어본다. AI에게도 그 허가를 줘야 한다. 패턴 ①(계획 먼저)과 세트로 쓰면 큰 작업의 안전망이 이중이 된다.

😤 안 고쳐지는 말

😎 한 번에 고쳐지는 말

"제목이 두 줄로 넘쳐. 한 줄에 들어가게 글자를 줄여줘" — 어디를, 어떻게 바꿀지가 다 들어 있습니다.

첫 결과가 완벽하길 기대하는 순간 실망한다. 사람 디자이너와 일할 때도 시안 → 피드백 → 수정을 돈다 — 한 바퀴가 몇 분으로 줄었을 뿐. "더 좋게"가 왜 실패하는지는 CH1의 "빈칸은 평균으로"와 같은 이야기라고 연결.
CH 3 · 피드백 공식

피드백은 좌표 + 증상 + 원하는 상태로

📍 좌표어디가3번 장 · 오른쪽 차트 · 표의 두 번째 열
+
🤒 증상어떻게 이상한지두 줄로 넘친다 · 겹친다 · 숫자가 원본과 다르다
+
🎯 원하는 상태어떻게 돼야 하는지한 줄로 · 높이를 맞춰 · 원본 합계와 같게
화면더 깔끔하게 해줘→3번 장 제목이 두 줄로 넘쳐. 한 줄로 줄이고, 7번 장 카드 3개는 높이를 맞춰줘.
문서너무 길어→2절 "배경"이 반 페이지야. 3줄로 줄이고, 줄인 만큼 결론을 앞으로 올려줘.
데이터숫자가 이상해→설비 B-07의 9월 합계가 1,284인데 원본 엑셀은 1,302야. 빠진 행을 찾아서 맞춰줘.

💡 한 번에 하나씩, 그리고 범위를 못 박습니다 — "제목만 고쳐. 나머지는 건드리지 마." 화면 부품의 이름(좌표)이 막히면 → UI/UX 용어 사전

이 장이 CH3의 핵심. 디자이너 옆에 앉아 모니터를 손가락으로 가리키며 말하듯 — 좌표가 손가락, 증상이 "여기 이상해", 원하는 상태가 "이렇게". 세 예시는 청중 업무에 맞게 바꿔 말해도 좋다. 원하는 상태를 빼면 AI가 고치는 방향을 또 추측한다는 점을 강조.
CH 3 · 보여 주기

말로 어려우면 스크린샷, 그다음은 AI가 직접 보게

📸 ① 캡처해서 붙이고 한 줄
[스크린샷 붙여넣기]
빨간 동그라미 친 부분에서 범례가
차트를 가려. 범례를 차트 아래로 옮겨줘.

캡처 위에 동그라미나 번호를 그려 넣으면 좌표가 더 정확해집니다. 지금 AI 도구는 대부분 이미지를 읽습니다.

🔍 ② AI가 스스로 보고 고치게
다 만들면 브라우저로 열어서 페이지마다
스크린샷을 찍어 봐. 글자 넘침·겹침·잘림을
찾아서 고친 다음, 다시 찍어서 확인해줘.

Claude Code 같은 에이전트는 브라우저를 직접 열어 볼 수 있습니다. 내가 매번 확인하던 일을 루프 안으로 넘기는 것 — 마지막 확인만 내 눈으로.

스크린샷 피드백은 실제로 시연하면 반응이 가장 좋다. 캡처 → 그림판/캡처 도구로 동그라미 → 붙여넣기. ②는 에이전트 환경(Claude Code 등)에서 가능하다. 브라우저 자동화 도구가 없는 환경이면 ①만 안내. 사내 화면을 캡처할 때는 회사 기밀·실데이터가 찍히지 않았는지 확인하고, 사내 승인 도구에서만.
CH 3 · 복구 문장

막혔을 때 — 증상별 복구 문장, 그대로 붙여 넣으세요

😵 빨간 에러가 났다이 에러 메시지 그대로야: [붙여넣기]. 원인을 한 줄로 말하고 고쳐줘.
⬜ 화면이 하얗게만 나온다화면이 비어 있어. 브라우저 콘솔 에러를 확인하고 고쳐줘.
🎯 엉뚱한 데까지 바뀐다표 정렬만 고쳐. 다른 부분은 한 글자도 건드리지 마.
↩️ 고쳤더니 더 나빠졌다방금 수정은 취소하고, 직전 버전으로 되돌려줘.
🔁 같은 실수를 반복한다이 방법은 세 번 실패했어. 완전히 다른 접근 두 가지를 제안해줘.
🧶 대화가 길어져 헷갈려 한다지금까지 상황을 5줄로 요약해줘. → 새 대화를 열고 그 요약부터 붙여 넣기

🔧 콘솔 여는 법: F12 → Console 탭 → 빨간 줄 복사  ·  🛟 "되돌려줘"가 확실하려면 세이브 포인트(커밋)가 있어야 합니다 → Git & GitHub

할 일은 진단이 아니라 전달 — 증상만 정확히 넘기면 원인은 AI가 찾는다. "안 돼요·에러 나요·이상해요"는 아무 정보가 없다. "콘솔 에러 확인하고 고쳐줘"는 화면이 백지일 때(스크립트 오류) 가장 잘 듣는다. F12는 처음 보는 분이 많으니 한 번 시연. "새 대화로 다시 시작"이 왜 먹히는지는 context 덱(컨텍스트 창)에서 자세히.
CH 3 · 루프가 헛도는 날

세 바퀴째 같은 증상이면 — 멈추고 방법을 바꿉니다

🚨 헛도는 신호

  • 같은 에러가 세 번째 나온다
  • 하나를 고치면 다른 곳이 깨진다
  • AI가 "이제 해결됐습니다"만 반복한다

🧭 이 순서로 빠져나옵니다

  1. 되돌린다 — 마지막으로 잘 되던 버전으로
  2. 새 대화 — 상황 요약 + 파일만 들고
  3. 원인부터 — "고치지 말고 먼저 원인 후보 3개와 확인 방법을 알려줘"
🐞 고칠수록 꼬일 때 — AI와 함께 디버깅하기재현 → 가설 → 로그로 원인을 좁히는 법은 디버깅 덱에서 자세히 다룹니다. debugging/ ↗
다듬기 루프는 "무엇을 원하는지"가 문제일 때 듣는다. 같은 증상이 반복되면 문제는 지시가 아니라 원인 — 그때부터는 디버깅이다. 여기서는 빠져나오는 순서만 짚고, 재현·가설·로그는 debugging 덱으로 넘긴다.

  2. API 키·비밀번호는 코드·대화·커밋에 남기지 않는다 — 새어 나갔다면 삭제가 아니라 재발급.
  3. 회사 정책이 이 자료보다 우선한다. 자세히 → security/
숙제는 하나: 매주 하는 업무 하나를 오늘의 프레임으로 시키고, 잘 나온 지시문을 저장하기 — 세 번 쓰게 되면 agent-skills 덱으로. 보안 약속은 시리즈 공통 문구다. 견본·스크린샷을 붙이는 오늘 기술과 직접 닿으니 꼭 읽고 넘어간다.
