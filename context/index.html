(여담: 컨텍스트 외에도 권한 확인·샌드박스 같은 안전장치 역할도 한다 — 질문이 나오면 언급.) 같은 모델이라도 하네스가 다르면 다르게 일한다 — Claude Code, Codex, Antigravity CLI, opencode가 서로 다른 이유.

가득 차면: 압축과 망각

92% — 한계 임박

한계선을 넘으면 자동 압축 — 과거 대화가 요약본으로 교체되고, 세부 결정·이유·예외가 사라집니다.

가득 차기 전에 이미 나빠집니다 — context rot

한계선(auto-compact 약 80%)을 넘으면 자동 압축이 일어나 과거 대화가 요약본으로 교체된다. 요약은 손실 압축이라 세부 결정·이유·예외 사항이 사라진다 — "아까 말했잖아"가 통하지 않는 순간이 온다. 그리고 가득 차기 전에 이미 나빠진다(context rot): 중간에 있는 정보를 놓치고(lost in the middle), 오래된 지시는 최신 잡음에 밀린다.

압축의 실체 — zip이 아니라 "요약해서 갈아끼우기"

LLM이 쓴 요약문으로 원문 히스토리를 통째로 교체합니다 — zip과 달리 복원 불가.

파일 압축(zip·jpg)은 알고리즘이 계산하고 zip은 100% 복원된다. compaction은 LLM에게 "지금까지를 요약해줘"라고 시킨 뒤 그 요약문으로 원문 히스토리를 통째로 교체하는 것이다. 무엇을 남길지는 요약 모델의 추측이므로, /compact "auth 버그 수정 내용 위주로 남겨줘"처럼 남길 것을 직접 지시할 수 있다.

# ✅ 좋은 예
"이 함수의 속도를 개선해줘.

로그 30,000줄 전체를 붙여넣으면 한 번에 상자의 20~25%가 잡음으로 채워지고, 정작 중요한 에러 한 줄은 중간에 묻힌다(lost in the middle). 판단에 필요한 것은 마지막 에러 메시지와 "언제부터/무엇을 바꾼 뒤 발생했는지" 맥락 한 줄이다. 습관: 로그는 tail 또는 에러 grep 결과만 전달하고, 전체 로그는 파일로 두고 필요하면 에이전트가 직접 읽게 한다.

폐기 선언은 지우개가 아니라 덮어쓰기 ▸

옛 문장은 그대로 남습니다

대화 히스토리는 덧붙기만(append-only) 합니다 — 폐기를 선언해도 옛 문장은 남습니다.

# ✅ 그래도 선언하는 이유 — 최신·명시적 신호가 이깁니다
"이전의 SQLite 기반 접근은 폐기하고,
이제부터는 DuckDB + Parquet 기준으로 진행해줘."
# 옛 결정보다 더 최근 위치에, 더 명시적인 상위 지시가
# 추가되어 모델이 이를 따르게 됩니다

진짜로 상자에서 치우려면

① /clear · 새 세션 — 유효한 결정은 파일에 남기고
② /compact "SQLite 논의는 버려줘" — 요약에 반영
③ API의 context editing — 오래된 도구 결과를 자동 삭제

대화 히스토리는 append-only — "그 방식은 폐기해줘"라고 말해도 옛 문장이 지워지지 않고 폐기 선언이 뒤에 덧붙을 뿐이다. 그래도 선언이 효과 있는 이유: 더 최근 위치의, 더 명시적인 지시가 이기기 때문. 폐기할 것과 새 기준을 한 문장에 명시하는 게 요령이다. 진짜로 치우려면 /clear(결정은 파일로 옮기고), 지시가 있는 /compact, 또는 API 레벨의 context editing을 쓴다.

서브에이전트는 자기만의 새 상자(컨텍스트 창)를 받아 일한다. 수십 개 파일을 읽는 탐색, 장황한 테스트 로그 같은 지저분한 소비는 그 상자 안에서 끝나고, 본진에는 결론 몇 K만 돌아온다. 서브에이전트의 상자는 다 쓰면 통째로 버려진다. 함수로 지역 변수를 격리하고 반환값만 받는 것과 같은 원리 — 대량 탐색·병렬 조사 작업에서 특히 효과적이다.

MCP — 도구를 꽂는 표준 포트 — 방향키로 서버를 꽂아보세요 ▸

Model Context Protocol — 하네스에 외부 도구·데이터 소스(GitHub·Slack·사내 DB…)를 연결하는 공개 표준. "AI 도구의 USB-C 포트"라고 불립니다.

  • 🔧 기본 도구만 — 파일 · 터미널 · 검색24K
  • 🔀 + GitHub 서버 — 도구 35개의 이름·설명·파라미터+18K
  • 💬 + Slack 서버 — 도구 11개+12K
  • 📋 + Jira · 사내 DB 서버 …+18K
  • 첫 인사도 전에 36% — 도구의 정의도 전부 컨텍스트입니다.
    그래서 최신 하네스는 도구 이름만 올려두고 상세 스키마는 필요할 때 검색해 로드합니다(Tool Search). 안 쓰는 서버는 빼는 게 기본입니다.
MCP는 외부 도구·데이터 소스를 하네스에 연결하는 공개 표준("AI 도구의 USB-C"). 단 서버를 붙이는 순간 그 서버의 도구 정의(이름·설명·파라미터 스키마)가 전부 System 영역에 상주한다 — GitHub+Slack+Jira만 붙여도 첫 인사 전에 36%. 대응: 안 쓰는 서버는 빼는 게 기본, 최신 하네스는 Tool Search로 이름만 올려두고 상세 스키마는 필요할 때 로드한다.

1. 테스트 전체 실행 · 커버리지 확인
2. CHANGELOG 갱신 · 버전 태그
3. 스테이징 배포 → 스모크 테스트
   … (500줄)
본문 · ~2K — 관련 작업이 감지된 순간에만 
├─ reference.md   ← 37K짜리 상세 규칙
└─ scripts/check.sh ← 실행만, 코드는 상자 밖
부속 파일 · +α — 그 단계에 도달했을 때만

PROGRESSIVE DISCLOSURE — 단계적 공개 ▸

1평소: 모든 스킬의 frontmatter만 상주~50 tok/스킬
2관련 작업 감지 → 그 SKILL.md 본문만 로드~2K
3필요할 때만 부속 파일 읽기 · 스크립트 실행+α
매뉴얼을 통째로 외우게 하지 않고,
목차만 들고 있다가 필요한 장을 펴게 한다.

본문이 길어도, 부속 파일이 많아도 — 평소 비용은 frontmatter 몇 줄입니다.

스킬은 3단계 점진 공개로 동작한다: (1) 시작 시에는 모든 스킬의 YAML frontmatter(name+description)만 시스템 프롬프트에 상주 — 스킬당 약 수십~100토큰. (2) 관련 작업이 감지되면 그 스킬의 SKILL.md 본문만 로드(권장 5K 토큰 이하). (3) reference.md 같은 부속 파일은 해당 단계에 도달했을 때만 읽고, 스크립트는 실행만 하므로 코드가 컨텍스트에 들어가지 않는다. 그래서 스킬 폴더가 아무리 커도 평소 상주 비용은 frontmatter 몇 줄이다. CLAUDE.md(전부 상주)와의 결정적 차이.

같은 도구, 두 가지 연결법 — MCP vs CLI + Skill

과제: "열린 PR을 확인하고 리뷰 코멘트를 남겨줘" — GitHub에 연결하는 두 가지 방법

🔌 MCP 서버 직결

도구 35개의 이름·설명·스키마가 매 세션 로드 — 그날 안 써도

호출 결과(JSON)도 매번 상자를 통과

⌨️ CLI 도구 + Skill

상주는 frontmatter 몇 줄뿐

필요할 때: SKILL.md ~2K 로드 → gh pr list 실행. 모델은 이미 git · gh 사용법에 익숙

쓰지 않는 날의 상주 비용: 18K vs 0.05K — 약 1/300

⚖️ 단, 만능 공식은 아닙니다 — MCP가 정답일 때

🔐 원격 서비스 + OAuth 인증  ·  🚫 셸·CLI가 없는 실행 환경(웹 챗 등)  ·  👥 다중 사용자 권한·감사 로그가 필요한 제품

MCP도 진화 중 — Tool Search(스키마를 필요할 때만 로드) · 코드 실행 결합으로 150K→2K(−98.7%)

같은 GitHub 작업이라도: MCP 직결은 도구 수십 개의 정의(이름·설명·JSON 스키마)가 매 세션 시스템 영역에 로드된다 — GitHub 공식 MCP는 수만 토큰을 차지하는 것으로 유명하다. CLI+Skill 패턴은 기능을 CLI(gh 등)로 두고, 사용법을 스킬로 적어둔다. 평소에는 frontmatter 몇 줄만 상주하고, 필요할 때 SKILL.md 본문(~2K)을 읽어 CLI를 실행한다. 모델은 방대한 학습 데이터로 git·gh 같은 CLI 패턴에 이미 익숙하다. 단 CLI+Skill이 항상 이기는 것은 아니다: (1) 원격 서비스 + OAuth — 자격증명을 붙여넣지 않고 안전하게 연결하려면 MCP가 사실상 유일한 표준. (2) 셸·코드 실행이 없는 환경(웹 챗, 일부 샌드박스)에서는 CLI 자체를 못 쓴다. (3) 다중 사용자 대행·테넌트 격리·감사 로그가 필요한 제품에서는 MCP의 구조화된 프로토콜이 맞다. 인터페이스가 단순하고 로컬 개발 환경이라면 CLI+Skill이 유리한 경우가 많다. MCP 진영의 대응: Tool Search(도구 이름만 올려두고 스키마는 검색 시 로드), 코드 실행과 결합해 도구를 코드 API로 감싸면 150K→2K(−98.7%, Anthropic 공식 블로그).

사내 환경: 효율을 넘어 보안

상자에 담는 것 = 외부 모델로 나가는 것

상자에 무엇을 담느냐는 곧 무엇이 외부 모델로 나가느냐의 문제다. 고객명·수율·장비명·내부 URL이 무심코 섞여 나갈 수 있다. 사내 Agent에는 내부 코드·문서·로그를, 사외 Agent에는 일반 개념·공개 문서·민감 정보를 제거해 추상화한 문제를 준다.

🏢 사내 Agent에는

내부 코드 · 내부 문서 · 사내 로그 · 보안이 필요한 데이터

🌐 사외 Agent에는

일반 개념 설명 · 공개 문서 · 샘플 코드 · 민감 정보를 제거해 추상화한 문제

# ❌ 원본 그대로
"Pixel ABC 프로젝트의 장비 X에서
wafer Y 수율이 72.3%로 떨어졌고…"
# ✅ 재구성된 context
"어떤 제조 데이터 분석 파이프라인에서
특정 배치의 품질 지표가 급락했을 때,
원인 분석용 Python 구조를 어떻게 설계하면 좋을까?"
사외 Agent에는 "원본 context"가 아니라 민감 정보를 제거한 재구성 context를 주세요.
