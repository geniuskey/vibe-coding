Git을 쓰면

파일은 하나. 바꿀 때마다 "언제·무엇을·왜"가 기록됩니다.

"3월 9일 버전으로 돌아가줘"가 언제든 됩니다.

코드만이 아니라 폴더 안의 모든 파일에 쓸 수 있습니다.

"버전 관리"라는 말이 어렵게 들려도, 다들 이미 파일 이름으로 손수 버전 관리를 하고 있다. Git은 그걸 파일 하나 + 자동 기록으로 바꿔 주는 도구일 뿐이다. 이 비유에 충분히 머문다.

🎮 잘 될 때 저장

게임에서 보스전 전에 저장하듯, 기능 하나가 잘 될 때마다 커밋합니다.

🕰 한 문장으로 되감기

"아까 잘 되던 걸로 돌려줘"면 복구됩니다. 그래서 실험이 두렵지 않습니다.

🤖 조작은 에이전트가

코딩 에이전트는 git을 잘 다룹니다. 여러분은 원하는 결과만 말하면 됩니다.

AI는 한 번에 파일 여러 개를 고칩니다. 잘 되던 상태를 잃기도 그만큼 쉽습니다 — "기능 하나 = 커밋 하나".
바이브 코딩에서 특히 중요한 이유: 사람이 손으로 짤 때보다 한 번의 변경이 크고 빠르다. 잘 되는 상태를 잃어버리기도 쉽다. 권장 리듬은 "기능 하나 = 커밋 하나". 하루 끝에 한 번 몰아서 하는 게 아니다.

CH 1 · GIT, 딱 필요한 만큼

GitLab·Bitbucket도 같은 역할의 서비스입니다. 오늘은 회사가 쓰는 GitHub 기준으로 설명합니다.

CH 2 · 사내 GITHUB

GitHub는 두 개 — 업무 코드는 사내 GitHub에만

🌍 github.com

인터넷의 GitHub · 개인 이메일로 만든 개인 계정

· 오픈소스, 개인 공부, 토이 프로젝트용
· Public 저장소는 전 세계 누구나 봅니다

🏢 github.company.net

회사가 관리하는 GitHub Enterprise · 회사 계정(SSO)

· 업무 코드·문서는 반드시 여기
· 회사 설정에 따라 사내망에서만 열립니다

🚨 둘은 화면이 거의 똑같습니다. 올리기 전에 주소창을 보세요 — 다른 것은 주소, 계정, 그리고 "누가 볼 수 있는가"입니다.
오늘 가장 중요한 장 중 하나. GitHub Enterprise = 회사가 직접 설치해 운영하거나 계약해 관리하는 GitHub. 생김새가 같아서 사고가 난다 — 주소창을 확인하는 습관이 핵심. 발표 전에 상단 SEMINAR_CONFIG(또는 ?ghe= 파라미터)로 회사 도메인을 맞춰 둘 것. 사내망 전용 여부도 회사마다 다르다.

🔍 에이전트에게도 알려 주기

"이 프로젝트의 원격 저장소는 사내 GitHub야" 한 번이면 주소를 헷갈리지 않습니다.

판단 기준을 질문 하나로 줄였다 — "회사 것이 조금이라도 섞였나?" 섞였거나 애매하면 사내. 외부 공개 절차·오픈소스 기여 절차 같은 세부 규정은 사내 문서 링크로 안내한다.

git이 내 이름으로 기록하게 설정합니다

배우는 것 — 커밋에는 "누가 했는지"가 남습니다. 처음 한 번만 이름과 회사 이메일을 알려 주면 됩니다.

💬 에이전트에게 이렇게 말하세요

🔧 수동으로 하려면

✅ 완료 기준

  • 에이전트가 git version 2.x처럼 버전 번호를 보여 준다
  • 설정된 이름·이메일이 화면에 출력된다
  • 브라우저에서 github.company.net에 로그인된다

🧯 막히면

설치 권한이 없다는 메시지 → 사내 소프트웨어 설치 절차로. 사내 GitHub 계정이 없다면 오늘은 짝꿍 화면으로 따라갑니다.

사내 GitHub 계정 발급·최초 로그인 절차는 회사마다 다르다 — 사내 온보딩 문서 링크를 여기서 안내. 시간을 아끼려면 세미나 공지에 준비물(에이전트 설치, git, 사내 GitHub 로그인)로 미리 보내 둔다. 실습 폴더가 없는 사람: "간단한 index.html 하나 만들어줘"로 바로 만든다 — 오늘 끝에 이 파일이 웹 주소로 열린다.
🖐 실습 1 · 첫 세이브 포인트 (5분)

내 폴더를 저장소로 만들고 첫 커밋을 남깁니다

배우는 것 — 커밋 한 번 = 되돌아올 수 있는 지점 하나. 민감한 파일은 처음부터 기록에서 뺍니다.

💬 에이전트에게 이렇게 말하세요
이 폴더를 git 저장소로 만들고 "첫 버전"으로 커밋해줘.
.env·키·개인 데이터 파일이 있으면 커밋 전에
.gitignore에 넣고 무엇을 뺐는지 알려줘.

🔧 수동으로 하려면

git init && git add -A && git commit -m "첫 버전"

✅ 완료 기준

  • "커밋 목록 보여줘" → 첫 버전 한 줄이 보인다
  • "커밋 안 된 변경 있어?" → 없다고 답한다
  • 제외한 파일이 있으면 그 목록을 들었다

🧯 막히면

"Author identity unknown" → 실습 0의 이름·이메일 설정을 다시. 폴더 안의 숨은 .git은 기록 보관함이니 지우지 않습니다.

방금 일어난 일: 폴더 안에 숨은 .git(기록 보관함)이 생기고 세이브 포인트 1호가 기록됐다. .git을 지우면 기록이 통째로 사라진다. 커밋 메시지도 맡길 수 있다 — "적당한 메시지로 커밋해줘"라고 하면 변경 내용을 요약해 쓴다. .gitignore를 첫 커밋부터 챙기는 이유: 한 번 커밋된 파일은 지워도 기록에 남는다.

✅ 완료 기준 — 3 · 브라우저 새로고침

  • 저장소 페이지에 내 파일 목록이 보인다
  • 맨 위에 커밋 메시지 첫 버전이 보인다
  • .env 같은 제외 파일은 안 보인다

🧯 막히면

  • 비밀번호·토큰을 묻는다 → "사내 깃헙 인증 방법 알려줘". 보통 Personal access token이나 SSO 승인입니다.
  • 토큰을 대화창에 붙여 넣지 마세요 — 로그인 창이나 자격 증명 관리자에 넣습니다.
가장 많이 막히는 곳은 인증이다. 회사 인증 방식(PAT, SSH, 자격 증명 관리자, SSO 승인)을 발표 전에 확인해 여기서 직접 시연한다. 공개 범위: Private(나와 초대한 사람) / Internal(사내 전원). 회사 정책에 맞게 안내. 토큰을 채팅에 붙여 넣는 실수가 잦다 — 보안 약속 2번(키는 대화에 남기지 않는다)과 연결해 짚는다.

  • 사내 GitHub 저장소의 커밋 수가 2가 된다
  • 두 번째 커밋을 눌러 바뀐 줄(초록·빨강)을 본다
STEP 2(확인)를 강조한다 — 잘 되는 상태에서 커밋해야 세이브 포인트에 의미가 있다. 두 번째 커밋 화면에서 초록(추가)·빨강(삭제) 줄을 보여 주면 "기록이 남는다"가 눈으로 이해된다. 커밋 타이밍은 하루의 끝이 아니라 기능 하나가 잘 될 때마다.
🖐 실습 4 · 되돌리기 (5분)

망했다? 한 문장이면 마지막 커밋으로 돌아갑니다

💬 방금 AI가 망쳤을 때
마지막 커밋 이후의 변경을 버리고 마지막 커밋 상태로 되돌려줘.
💬 예전에 잘 되던 버전으로
최근 커밋 목록을 보여줘. 어제 오후에 잘 되던 버전으로 돌아가고 싶어.

🔧 수동으로 하려면

git log --oneline   # 세이브 포인트 목록
git restore .       # 커밋 안 한 변경 버리기
git revert HEAD     # 마지막 커밋을 취소하는 커밋

✅ 완료 기준 — 일부러 망가뜨려 보기

  • "index.html 내용을 전부 지워줘" → 브라우저에서 빈 화면 확인
  • 첫 번째 프롬프트로 복구 → 새로고침하면 원래 화면

🧯 되돌려도 같은 에러가 반복되면

되돌리기는 응급처치입니다. 원인을 찾는 법은 → 고칠수록 꼬일 때 — AI와 함께 디버깅하기

실습: 일부러 파일을 망가뜨리고 한 문장으로 복구한다. "커밋 = 세이브 포인트"가 몸으로 느껴지는 순간. 이미 푸시한 커밋을 되돌릴 때는 기록을 남기며 취소하는 revert가 안전하다 — 에이전트가 상황에 맞게 고른다. "전부 삭제", "강제로" 같은 요청엔 에이전트가 되묻는다. 그 메시지는 읽고 답한다. 같은 에러가 되돌려도 반복된다면 디버깅 덱으로.

💬 끝나면 PR

🔧 수동으로 하려면

# 작업 후 push → 웹에서 "Compare & pull request"

✅ 완료 기준

  • 사내 GitHub의 Pull requests 탭에 내 PR이 열려 있다
  • Files changed에서 바뀐 줄이 보인다
  • Merge 후 main에 다크 모드가 들어온다

혼자 하는 프로젝트라면 당분간 main에 바로 커밋해도 됩니다. 동료와 같은 저장소를 쓰기 시작하면 이 장으로 돌아오세요.

PR 리뷰 화면을 웹에서 잠깐 시연(코멘트 달기, Merge 버튼). 사내 협업의 실제 모습이 여기서 보인다. AI가 쓴 코드를 PR로 받아 리뷰하는 법은 verification 덱에서 더 다룬다. Merge 후 정리는 "합쳐진 브랜치 정리해줘".

실전에서 가장 자주 펼칠 장. "에러 메시지를 통째로 붙여 넣기"를 강조한다. 푸시 거부 때 "강제 푸시는 하지 마"를 붙이는 이유: 동료의 작업을 덮어쓸 수 있다. 키 유출은 기록에서 지우는 것보다 재발급이 먼저 — 한 번 푸시된 키는 누군가 봤다고 가정한다(보안 약속 2번).
